## 2. Р — умови 0.8.1б закрито обома виконавцями

Моя умова Н-1 з 0.8.1б (**явний rowid 2⁶³−1 на старій базі записано як «запобіжна», не «заборонено»**) — **закрита**.

| Умова | 0.8.1б | 0.8.1в (Атанор / еталон) |
|---|---|---|
| Явний rowid 2⁶³−1 на старій базі, 6 форм (`атака17_спроби`, `атака17_rowid_варіанти`, `rowid_сам`): літерал, `806+1`, параметр `?`, `SELECT`, `OR REPLACE`, `count(*)+…` | «запобіжна», «спроб немає» | ✓ / ✓ **«заборонено»** — «випадковість SQLite (таблиця «t» — рядок отримав би rowid 2⁶³−1…)», як на далекій базі (13 / 13 і 4 / 4 «заборонено») |
| `UPDATE t SET rowid=2⁶³−1` на старій базі | «заборонено» | ✓ / ✓ «заборонено» (без змін) |
| `sqlite_dbpage` — читання і запис (Скептик `сирі_сторінки_дія`) | діра (писало повз authorizer) | ✓ / ✓ **«заборонено: сирі сторінки бази (sqlite_dbpage): запис повз SQL, authorizer і тригери»** — і на `SELECT count FROM sqlite_dbpage`, і на `UPDATE … SET data` |
| Квота ≤1 вичерпана невинним INSERT, далі ATTACH/`random`/`date('now')`/`pragma_database_list`/rowid 2⁶³−1 (Аудитор `квота_порядок`) | `random`/date/rowid ховалися за «квоту вичерпано» | ✓ / ✓ ATTACH, random, date('now'), PRAGMA — **«заборонено» після квоти**; лише rowid 2⁶³−1 і невинний INSERT — «квоту вичерпано», і слід чесно додає: «права перевірено й до неї — лише rowid, який дав би запит SQLite, без виконання не перевірити» |

Невинні описки на старій базі — тепер звичайна помилка (моє побажання 0.8.1б виконано): `INSERT INTO t(y)` →
«немає стовпця», `немає(x)` → «немає такої таблиці», `INSERT …(1` → «незавершений запит» (а не «заборонено»),
обома виконавцями.

## 3. Н — нове на виправленнях (`атака18_*`), коротко

- **Вузький залишок не можна сфабрикувати зсередини Nigredo.** Щоб поставити `sqlite_sequence` на край, спробував
  `INSERT INTO sqlite_sequence(rowid,…) VALUES (9223372036854775806, …)` — сам по собі **«заборонено»**: «системна
  таблиця «sqlite_sequence»: INSERT і зміна rowid — лише з правом «жереб», бо з rowid 2⁶³−1 наступний рядок SQLite бере
  навмання». Отже дістатися запобіжної відмови без «жереб» можна лише на вже-наявній старій базі, не створити її самому.
- **Сховати спробу за запобіжною не вдалося.** У тому самому запиті, що цілив би в залишок (`INSERT INTO d SELECT
  random()` на межі), `random` спіймано першим — **«заборонено»**, не запобіжна. authorizer+байткод біжать раніше.
- **Точна лічба прибрала хибну відмову.** На старій базі із запасом 2³² нова AUTOINCREMENT-таблиця й дві вставки —
  **звичайна робота** (без запобіжної), обома виконавцями. `q`, що вичерпала номери, — рідна відмова SQLite (SQLITE_FULL),
  а не «заборонено»/запобіжна.
- **Права без дії бачать байткод.** Квота (вище) — закрито. `--сухо`: ATTACH і `sqlite_dbpage` — «заборонено»
  (статичний розбір); `random`/`date('now')`/`CURRENT_DATE` у **бд.читати** (читання під `--сухо` виконується) —
  «заборонено». У придушених **бд.писати** ці ж дії не компілюються, тож ідуть у перелік «дій не виконано» (✓ з
  впевненістю 0), а `--сухо` прямо попереджає «справжній запуск може піти іншим шляхом». Не ховає, не бреше — лише
  асиметрія «читання бачить / придушений запис перелічує». Заявлене «--сухо бачить random()/date('now')» — так, на тому
  шляху, що виконується.
- **Інших шляхів до сирих сторінок немає.** `CREATE VIRTUAL TABLE … USING dbstat` і `… USING fts5(a)` — **«заборонено:
  CREATE_VTABLE»**, обома виконавцями.
- **Слід ключем власника.** `nigredo_pereviryty_slid` з кодом на запуску `атака18_вузький`: «✓ слід цілий… саме від цієї
  програми» (sha256 збігся), підписаний. Дію поза печаткою чи дозволами не знайшов.

**Атанор = еталон** на всіх ~13 парах прогонів (ідентичні вивід і число записів сліду, зокрема звичайна робота — 478
записів у кожного). Розбіжностей 0, коду 4 і зависань немає.
