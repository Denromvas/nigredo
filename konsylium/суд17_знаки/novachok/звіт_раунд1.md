## 2. П — потреба й задум

- Гліфи `η`, `ω`, `γ` потрібні агентові, не лише самохостингу. Задачі, де я їх би взяв: нормалізація імен з різних джерел (`η` звітує «той самий текст» для é і e+наголос); чистка тексту від невидимих знаків (`γ` з «Cf»); перевірка вводу на керівні знаки (`γ` «Cc», `ω` для коду). Усе це можна зробити й через `δ` над JSON з `\\uXXXX`, але `ω` дає це без обхідного шляху (пробував: `ω 8238` і `δ "\\u202e"` дають однаковий вивід, див. §6).
- Чого бракує одразу (з того, що я перевірив чи бачив у тексті): шістнадцяткового запису коду немає (його пишуть вручну, `гекс` у заявленому прикладі `examples/znaky.ngr` — окрема функція), NFKC, письма знака. Це не дефект, а межі, які заява автора вже називає.
- Чи не забагато: `γ` і `ω` можна було б зробити наявними функціями (`категорія(знак)` тощо), але гліф — коротший запис і без нової назви. Я не бачу, що саме `γ` мав би стати функцією замість гліфа; рішення на користь гліфа виглядає розумним.
- Знаки: `η` поруч із `ν` і `μ` — читається. Двобічний `ω` (знак ↔ код) пояснений у ДЛЯ_АГЕНТІВ.md:212 і SPEC.md:155, але без прикладу `ω 769` (записи «знак | код» в одному гліфі новачкові неочевидні).

## 3. З — значення

Перевірено трьома виконавцями (Атанор, еталон, Альбедо), вивід однаковий у кожному випадку:

- NFC, порядок знаків поєднання: `e` + 803 + 769 → `7865 769` (ẹ + акут, без складання); `a` + 769 + 803 → `7841 769`; `e` + 808 + 769 → `281 769`. Порядок ccc виконано.
- Заступлене складання: `A` + 778 + 769 → `506` (Ǻ, другий рівень); `A` + 776 + 772 → `478` (Ǟ). Правильно за UAX #15.
- Хангиль: `4352 4449 4520` → `44033` (각); `44033 4520` (LVT + T) лишається `44033 4520`; `4352 4449` → `44032`.
- Синглтони й розклади: Å U+212B → `197`; U+0340 (832) → `768`; U+0344 (836) → `776 769`.
- Виключення складання: U+1D15E (119134) → `119127 119141` (розклад, без складання).
- Другий рівень: `A` + 778 + 769 → `506` (Ǻ), тобто складання йде через проміжний Å; `193 778` для `A` + 769 + 778 (Á з кільцем, складання немає) — правильно.
- η η x = η x: `η η` від `e`+769 → `233` (= η x), як в SPEC.md:154.
- Кроки: `η` лінійний: 20 символів → 27 кроків, 40 символів → 52 кроки (SPEC.md:160 «за розмір» виконано). `ω 97` і `γ ω 97` — це кроки всієї програми (5 і 6), окремо ω не міряв.
- Межі `ω`: 0, 10FFFF (1114111), D7FF (55295), E000 (57344) — приймаються; 55296 (сурогат), 1114112, −1, 0.5, рядок з 2 знаків, порожній рядок — помилка, однаково в трьох виконавцях (`✗ 2:3 ω: коду 55296 серед знаків Unicode немає…`).
- Межі `γ`: 0 Cc; 57344 Co; 1114111 Cn; 8293 (U+2065, не призначено) Cn; 178000 Lo; 65 Lu; 44032 Lo; 769 Mn; 8232 Zl; 127462 So; 8203 Cf; 895 (U+037F, Unicode 14) Lu; 32 Zs; 47 Po; 10 Cc; 2 Cc — усе за стандартом.
- Не перевірено: знак, призначений лише в 15.1 (наприклад U+2EBF0), так що «Unicode 15.1» на новому знаку не бачив.
- Порожній рядок для `η`: `η ""` не пробував; `γ ""` і `ω ""` — помилка («рядок із 0 знаків»).
- Рядок на мільйон знаків і `η` над ним не міряв (машина спільна).

## 5. С — сумісність

- Правило «Нові гліфи в 1.x» (SPEC.md:923–927) перевірено нормою 1.3 (`ngr`) на позиціях: імʼя (`ω 65` → `2:3 невідомий гліф «ω»`), параметр лямбди (`λη` → `2:14 невідомий гліф «η»`), гліф (`η «ab»`, `γ «a»`). Усі відхилено до запуску з кодом 2 (`ngr с1.ngr` → «Exit code 2»). У коментарі (`※ η ω γ`) і рядку (`「η ω γ」`) 1.3 приймає — ці місця й давали б «жодної програми 1.0–1.3», тож правило тримається на перевірених позиціях.
- Норма 1.3 на `examples/znaky.ngr` (1.4) → відмова на рядку 5, позиція 30 (`η`): «невідомий гліф». Очікувано.
- Не перевірив: позицію ключа словника без лапок, імʼя модуля, імʼя субагента, інструмента — лише імена, параметри й гліфи; набору `tests/сумісність/` не запускав; норми 1.0–1.2 не мав, тож «1.0 не міг» перевіряв тільки через 1.3.
- Програма, що в 1.3 працює, а в 1.4 дає інший вивід: не знайшов. Наявні тестові програми (`ngr` vs `ngr17`) для цього не запускав.
- Про `γ` непризначених знаків: SPEC.md:1022–1023 чесно каже, що може змінитись з новішими таблицями. Це узгоджується з тим, що `γ` дав `Cn` для 8293 й 1114111.
